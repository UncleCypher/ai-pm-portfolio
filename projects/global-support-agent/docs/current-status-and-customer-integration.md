# 全球智能售后客服 Agent（以 MOVA 为案例）：当前建设状态与客户接入说明

> **项目性质声明：**本项目是个人独立完成的 AI 产品概念验证，以 MOVA 智能家电业务作为公开案例研究。项目未受 MOVA 或其关联公司委托，不代表 MOVA 官方产品、合作项目或正式交付，也未使用 MOVA 内部数据、真实用户数据或未公开业务资料。

## 1. 文档目的

本文说明全球智能售后客服 Agent 当前已经完成的能力、尚未完成的能力、未完成原因、需要未来合作客户提供的数据与系统，以及客户现阶段和正式生产阶段应调用的 API。文中的 MOVA 仅作为智能家电行业案例。

本文区分三个成熟度阶段：

- **演示验证版（当前）**：可在本地运行，用于验证交互、自然语言理解、安全分流和诊断思路。
- **客户试点版**：接入客户真实知识和部分业务系统，供内部客服或小范围用户使用。
- **生产正式版**：具备认证、持久化、审计、监控、容灾、数据治理和正式 SLA。

当前项目处于：**演示验证版已完成，客户试点版尚未完成。**

### 2.2 自然语言理解

| 能力 | 状态 | 说明 |
|---|---|---|
| 中文自然语言理解 | 已完成 | 支持明确描述和部分模糊口语 |
| 英文自然语言理解 | 已完成 | 接口支持英文 locale 和英文问题 |
| 情绪识别 | 基础完成 | 当前仅区分平稳与负面 |
| 标准症状归一化 | 已完成 | 将自然语言映射为受控症状编码 |
| DeepSeek 接入 | 已完成 | 通过 OpenAI Chat Completions 兼容接口调用 |
| 模型结构化输出 | 已完成 | 使用 Pydantic 校验模型 JSON |
| 未知编码过滤 | 已完成 | 模型不能创建未经系统允许的正式故障编码 |
| 模型故障降级 | 已完成 | 超时、网络失败或非法 JSON 时回退到本地语义规则 |
| 回复语言锁定 | 已完成 | 中文页面不会因为模型语言判断而输出英文 |
| 分类体系外识别 | 已完成 | 模型可以标记 `out_of_taxonomy`，避免强行错误归类 |

当前模型只负责：

- 理解用户语言；
- 提取语义；
- 归一化问题；
- 选择标准症状编码；
- 标记分类体系外问题。

模型当前不负责：

- 判断是否在保修期；
- 决定退款或换新；
- 判断配件兼容；
- 决定高风险操作；
- 覆盖安全规则；
- 直接修改客户业务数据。

### 2.3 已实现的诊断范围

当前内置以下通用扫地机器人故障域：

1. 无法回充或找不到基站；
2. 配网失败或设备离线；
3. 基站水路或拖布清洗异常；
4. 吸力下降或清洁效果变差；
5. 异响或异常噪音；
6. 地图、定位或导航异常；
7. 卡困、越障或避障异常；
8. 自动集尘失败；
9. 续航缩短或充电不充分。

每个已知故障域目前包含：

- 标准症状编码；
- 常见自然语言表达；
- 2～3 个候选原因；
- 初始置信度；
- 一项低风险排查动作；
- 模拟知识引用。

重要限制：

> 当前诊断内容是通用演示知识，不是 MOVA 已审核的正式维修知识，不能作为正式售后结论直接投入生产。

### 2.4 安全分流

当前可以识别并立即停止自动诊断的危险场景包括：

- 冒烟、起火和烧焦味；
- 电池膨胀；
- 异常发热、发烫或过热；
- 漏电或水接近电源；
- 人身、宠物或财产损伤。

危险问题处理方式：

1. 提示立即停止使用；
2. 禁止继续充电、运行或拆机；
3. 生成模拟人工工单；
4. 不输出普通自助维修步骤。

当前安全规则是本地确定性规则，不依赖 DeepSeek 是否可用。

## 4. 需要客户数据或客户系统才能完成的部分

这类能力不能由开发方凭空构造。客户需要提供经过脱敏、授权和确认的数据或接口。

### 4.1 MOVA 正式产品知识库

当前缺失：

- 完整产品型号和区域版本；
- 硬件版本；
- 固件版本及适用范围；
- 官方错误码；
- 官方用户手册；
- 客服 FAQ；
- 售后排查 SOP；
- 维修技术公告；
- 已知质量问题；
- 配件兼容关系；
- 国家和渠道售后政策。

客户需要提供：

| 数据 | 最低要求 |
|---|---|
| 产品主数据 | 型号、区域、硬件版本、上市状态 |
| 错误码字典 | 错误码、含义、适用版本、处理动作 |
| 售后 SOP | 症状、检查条件、步骤、风险、人工升级条件 |
| 产品手册 | 当前有效版本及适用型号 |
| 配件关系 | 配件编码、适用型号和地区 |
| 政策数据 | 质保期、部件范围、例外规则、生效日期 |

没有这些数据时，系统只能提供通用演示建议，不能保证适用于具体 MOVA 型号。

### 4.2 历史售后案例

当前缺失：

- 用户原始问题；
- 设备型号和固件；
- 客服实际排查步骤；
- 维修人员确认的最终根因；
- 更换部件；
- 是否换新或退货；
- 问题是否复发；
- 用户满意度。

客户数据用途：

- 建立真实症状分类；
- 调整候选原因概率；
- 建立诊断评测集；
- 发现容易混淆的问题；
- 衡量 Agent 是否真的解决问题；
- 发现批次、型号或固件异常。

最低建议数据量：

- 试点前：500～2,000 条已闭环、已脱敏案例；
- 正式上线前：覆盖主要型号和高频故障的分层评测集；
- 数据必须包含最终处理结果，只有聊天记录而没有最终根因的数据价值有限。

### 4.3 设备 IoT 与日志接口

当前未接入：

- 设备在线状态；
- 固件版本；
- 电池、电压和温度；
- 传感器状态；
- 最近错误码；
- 清洁任务轨迹；
- 基站状态；
- 设备日志。

客户需要提供受控 API，而不是数据库直连。建议接口：

```text
resolve_device_identity
get_device_status
get_device_logs
get_recent_error_codes
get_firmware_version
```

客户还需要明确：

- 哪些字段属于敏感数据；
- 是否需要用户授权；
- 数据保存期限；
- 地图、摄像头和家庭信息是否允许使用；
- 不同国家的数据是否需要区域隔离。

### 4.4 CRM、工单和人工客服系统

当前工单是内存中的模拟对象：

```text
FAKE-00001
```

服务重启后模拟工单不会保留，也不会进入客户客服系统。

客户需要提供：

```text
create_ticket
update_ticket
get_ticket_status
assign_ticket
request_human_review
append_diagnosis_summary
```

需要明确：

- 工单字段；
- 优先级规则；
- 人工队列；
- SLA；
- 国家和语言路由；
- 幂等规则；
- 回调或状态同步方式。

### 4.5 订单、质保、配件和物流

当前未接入：

- 订单查询；
- 购买日期；
- 销售渠道；
- 质保状态；
- 配件库存；
- 维修网点；
- 寄修与物流状态。

客户需要提供：

```text
get_order
check_warranty
check_part_compatibility
check_part_inventory
find_service_center
create_repair_shipment
get_repair_status
```

没有客户接口时，Agent 不应回答“是否保修”“是否可以换新”或“某配件是否适配”。

### 4.6 客户身份与设备归属

当前接口不验证：

- 用户身份；
- 用户是否拥有该设备；
- 用户是否有权读取设备日志；
- 用户所在国家是否与设备销售地区一致。

客户需要提供：

- 用户认证方式；
- App 或官网令牌校验接口；
- 设备绑定关系；
- 授权范围；
- 企业客服身份和权限体系。

## 5. 不依赖客户数据，但因为尚未投入试点或生产而未完成的部分

这些能力主要属于生产工程建设。即使客户暂未提供业务数据，也可以开发；当前没有完成是因为项目仍处于演示验证阶段。

### 5.1 持久化多轮会话

当前状态：

- 每次请求基本作为一次独立诊断；
- `session_id` 会返回，但没有写入 PostgreSQL；
- 用户上一轮回答不会形成完整、可恢复的诊断状态；
- 服务重启后会话消失。

生产需要：

- PostgreSQL 保存会话、消息、证据、候选原因和步骤；
- Redis 保存短期状态和幂等锁；
- 支持暂停、恢复、转人工和超时；
- 限制最大诊断步数；
- 连续无进展时停止循环。

### 5.2 正式认证和 API 网关

当前状态：

- 无登录认证；
- 无 API Key 或 OAuth 校验；
- 无租户隔离；
- 无访问限流；
- 无 WAF 和防滥用策略。

生产需要：

- API 网关；
- OAuth 2.0、JWT 或客户单点登录；
- 用户、客服和管理员角色；
- 地区和租户隔离；
- IP、用户和渠道限流；
- 请求签名与重放保护。

### 5.3 数据库与知识发布系统

当前知识写在 Python 代码中。

生产需要：

- PostgreSQL 产品知识模型；
- pgvector 语义检索；
- 知识审核、发布、失效和回滚；
- 型号、地区、固件结构化过滤；
- 文档来源和引用；
- 运营人员可使用的知识管理后台。

### 5.4 异步和性能优化

当前模型请求为同步调用，适合演示，不适合大并发。

生产需要：

- 异步 HTTP 客户端；
- 连接池；
- Redis 语义缓存；
- 小模型与强模型路由；
- 请求超时和熔断；
- 后台任务队列；
- 图片、日志等耗时任务异步处理；
- P50、P95 和错误率监控。

### 5.5 审计和可观测性

当前没有完整生产审计系统。

生产需要记录：

- 请求 ID 和会话 ID；
- 模型名称和模型版本；
- Prompt 版本；
- 知识版本；
- 安全规则版本；
- 检索引用；
- 工具调用及耗时；
- 人工批准或驳回；
- 脱敏后的错误信息；
- DeepSeek 降级率和调用成本。

需要接入 OpenTelemetry、日志平台和告警系统。

### 5.6 部署、容灾和运维

当前通过本地命令启动：

```powershell
.\.venv\Scripts\python.exe -m uvicorn mova_support.api:app --reload
```

这是开发方式，不是生产部署方式。

生产需要：

- Docker 镜像；
- 测试、预发布和生产环境；
- Kubernetes、云容器或受控应用平台；
- 密钥管理系统；
- HTTPS 和正式域名；
- 多实例和负载均衡；
- 健康检查和自动重启；
- 数据库备份；
- 灰度、回滚和灾备；
- 明确 SLA。

### 5.7 安全与隐私合规

当前已经定义基础安全原则，但尚未完成正式合规建设。

生产需要：

- 数据分类分级；
- 用户授权页面；
- 数据最小化；
- 日志脱敏；
- 数据保留与删除；
- 中国、欧盟、美国等地区政策评审；
- 数据跨境评估；
- 模型供应商数据处理条款；
- 安全测试与渗透测试；
- 法务审批。

### 5.8 客服与运营后台

当前只有消费者演示页面，没有：

- 客服 Copilot 工作台；
- 人工接管；
- 会话队列；
- 工单编辑；
- 知识审核；
- 质量问题聚类；

建议客户试点时优先建设客服 Copilot，而不是直接向所有消费者开放。

## 8. 客户当前可以调用的 API

### 8.1 健康检查

```http
GET /health
```

响应：

```json
{
  "status": "ok"
}
```

用途：

- 本地开发检查；
- 部署平台存活检查；
- 自动化测试。

注意：当前健康检查只表示 API 进程可访问，不代表 DeepSeek、数据库和客户业务系统全部正常。生产版需要增加 readiness 检查。

### 8.2 当前诊断接口

```http
POST /api/v1/diagnose
Content-Type: application/json
```

请求示例：

```json
{
  "message": "机器运行一会后特别发烫",
  "locale": "zh-CN",
  "country": "CN",
  "channel": "web",
  "device_log_consent": false,
  "device": {
    "category": "robot_vacuum",
    "model": "P50 Ultra",
    "region": "CN",
    "serial_number": null,
    "firmware_version": "1.0.0",
    "app_version": null
  }
}
```

当前主要响应字段：

```json
{
  "request_id": "请求ID",
  "session_id": "会话ID",
  "language": "zh",
  "intent": "safety_incident",
```

## 9. 客户正式使用时建议调用的 API

正式产品不建议继续把所有动作压在单一 `/api/v1/diagnose` 接口中。建议采用会话式 API。

### 9.1 创建诊断会话

```http
POST /api/v1/sessions
Authorization: Bearer <customer-user-token>
Idempotency-Key: <unique-key>
```

用途：

- 验证用户身份；
- 验证设备归属；
- 确定国家、语言和渠道；
- 记录用户授权；
- 创建可持久化会话。

### 9.2 发送一轮用户消息

```http
POST /api/v1/sessions/{session_id}/messages
Authorization: Bearer <customer-user-token>
Idempotency-Key: <client-message-id>
```

这是 App、官网和客服工作台最主要调用的接口。

用途：

- 发送用户自然语言；
- 继续上一轮诊断；
- 返回追问、风险、候选原因和下一步；
- 触发一次受控工具调用；
- 必要时转人工。

### 9.3 提交诊断步骤结果

```http
POST /api/v1/sessions/{session_id}/steps/{step_id}/result
```

用途：

- 用户反馈“已完成”“仍未解决”等结果；
- 更新证据；
- 调整候选原因概率；
- 选择下一项检查。

### 9.4 查询会话

```http
GET /api/v1/sessions/{session_id}
```

用途：

- 恢复中断会话；
- 查看当前状态；
- App 与客服工作台同步。

### 9.5 请求人工接管

```http
POST /api/v1/sessions/{session_id}/handoff
```

用途：

- 创建或更新真实工单；
- 传递诊断摘要；
- 路由到对应国家和技能组；
- 返回真实工单 ID。

### 9.6 查询工单状态

```http
GET /api/v1/tickets/{ticket_id}
```

### 9.7 上传图片或视频

建议采用预签名上传：

```http
POST /api/v1/uploads
```

文件直接上传到对象存储，Agent 只接收文件 ID，避免大文件经过诊断 API。

### 9.8 知识和管理 API

仅供授权运营人员使用：

```text
POST /api/v1/admin/knowledge/import
POST /api/v1/admin/knowledge/{id}/review
POST /api/v1/admin/knowledge/{id}/publish
POST /api/v1/admin/knowledge/{id}/rollback
GET  /api/v1/admin/evaluations
GET  /api/v1/admin/unclassified-issues
```

上述正式 API **目前尚未实现**，是客户试点版的开发内容。

## 10. 客户系统如何调用

### 10.1 MOVAhome App

推荐方式：

```text
MOVAhome App
  -> 客户 API 网关
  -> MOVA 售后 Agent API
  -> IoT / CRM / 订单等客户内部服务
```

App 不应直接携带 DeepSeek API Key，也不应直接调用 DeepSeek。所有模型调用必须经过后端。

### 10.2 官网

官网聊天组件调用客户 API 网关，再由网关调用 Agent API。需要：

- 登录或匿名会话策略；
- CAPTCHA 和限流；
- 国家及语言识别；
- 人工客服转接。

### 10.3 客服工作台

客服工作台调用相同会话 API，但使用客服身份。可以返回比消费者更多的信息：

- 设备状态；
- 日志摘要；
- 详细候选原因；
- 内部维修 SOP；
- 不允许展示给消费者的备注。

消费者端和客服端必须通过权限控制区分字段，不能只依赖前端隐藏。

## 12. 推荐交付路径

### 阶段一：客户内部评审

目标：

- 确认诊断流程；
- 确认安全边界；
- 确认客户数据清单；
- 确认系统接口和部署方式。

当前版本已经可以支持该阶段。

### 阶段二：客服 Copilot 试点

范围建议：

- 一个国家；
- 3 个型号；
- 20 个高频问题；
- 10～20 名客服；
- 500～2,000 条历史案例；
- 只提供建议，由人工确认。

需要完成：

- PostgreSQL 多轮会话；
- 客户知识导入；
- 真实工单接口；
- 客服认证；
- 审计和评测。

### 阶段三：消费者灰度

仅开放：

- 低风险问题；
- 已审核知识；
- 可回退人工的问题；
- 可追踪的会话。

### 阶段四：正式上线

完成：

- 生产部署；
- SLA；
- 合规；
- 灰度与回滚；
- 监控告警；
- 全球地区和语言扩展。

## 13. 当前结论

当前项目已经证明以下技术路线可行：

- 使用 DeepSeek 理解自然语言；
- 将自然语言转换为结构化症状；
- 用确定性规则保护危险场景；
- 对已知问题提供候选原因和低风险步骤；
- 对未知问题进行引导或转人工；
- 提供可供前端调用的结构化诊断 API。

当前项目尚未具备正式生产条件，主要原因不是基础对话能力缺失，而是：

1. 缺少客户正式产品知识和真实售后数据；
2. 缺少客户 IoT、CRM、订单和质保接口；
3. 尚未建设持久化、认证、审计、性能、部署和合规能力；
4. 当前工单、知识和设备数据均为演示或模拟。

因此，当前最准确的产品定位是：

> **可用于客户需求确认和内部技术评审的全球售后诊断 Agent 演示验证版。**

客户正式使用时，主要调用的应该是未来的：

```text
POST /api/v1/sessions
POST /api/v1/sessions/{session_id}/messages
POST /api/v1/sessions/{session_id}/steps/{step_id}/result
POST /api/v1/sessions/{session_id}/handoff
```

而当前可用的：

```text
POST /api/v1/diagnose
```

仅适合演示、联调和试点前评测，不应直接视为完整生产接口。
