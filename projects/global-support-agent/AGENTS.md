# AGENTS.md

## 1. 项目概述

本仓库用于构建 **MOVA 全球售后诊断 Agent**。系统面向消费者与客服人员，通过多语言对话、产品知识检索、设备日志分析和受控工具调用，完成智能家电故障分诊、逐步排查、工单生成与售后流转。

当前为绿地项目。首版聚焦一个重点市场、扫地机器人品类、3 个主力型号和 10～20 个高频故障，不追求一次覆盖全部国家与产品。

首版技术栈约定：

- Python 3.12
- FastAPI：HTTP API 与流式会话接口
- Pydantic v2：领域对象与工具参数校验
- LangGraph：有状态诊断工作流；禁止开放式无限循环
- PostgreSQL：会话、案例、审计和结构化产品知识
- pgvector：知识检索；向量检索不能替代型号与版本过滤
- Redis：短期会话状态、限流和幂等锁
- pytest、Ruff、mypy：测试与静态检查
- OpenTelemetry：链路、模型调用和工具调用观测

核心原则：**LLM 负责理解、规划和解释；规则与业务系统负责事实、权限和高风险决策。**

## 2. 项目状态与目标

项目尚未初始化代码。首次开发任务应先建立最小可运行骨架，再实现业务能力。

MVP 必须支持：

1. 自动识别语言、意图、情绪、型号、症状和错误码。
2. 基于国家、型号、硬件版本和固件版本检索适用知识。
3. 维护候选根因及置信度，逐步选择下一项安全检查。
4. 在用户授权后读取模拟设备状态或真实 IoT 数据。
5. 对危险场景、低置信度和高成本动作强制转人工。
6. 生成结构化诊断报告和完整工单摘要。
7. 记录每次检索、推理、工具调用、规则判断和人工决策。

MVP 不包含：

- 自动退款、换新或大额补偿；
- 自动认定人为损坏；
- 未经授权读取摄像头、家庭地图或设备日志；
- 自动拆机指导、固件降级或危险维修；
- 完全自治、无步数上限的多 Agent 协商；
- 全品类、全国家和全渠道同时上线。

## 5. 核心领域模型

所有 Agent 节点必须读取和更新显式状态，不得依赖不可审计的自由文本作为唯一状态。

至少定义以下类型：

- `UserContext`：国家、语言、时区、渠道、用户授权。
- `DeviceIdentity`：品类、型号、区域版本、序列号、固件、App 版本。
- `Symptom`：标准症状码、用户原话、频率、开始时间、严重度。
- `Evidence`：来源、采集时间、内容摘要、可信度、隐私级别。
- `Hypothesis`：候选根因、置信度、支持证据、反对证据。
- `DiagnosticStep`：目的、操作、风险、预期结果、完成状态。
- `SafetyDecision`：风险级别、命中规则、允许动作、升级原因。
- `ToolResult`：成功状态、错误类型、幂等键、来源和时间戳。
- `DiagnosisOutcome`：已解决、需观察、需维修、需人工、无法判断。
- `AuditEvent`：会话、节点、输入摘要、输出摘要、模型及规则版本。

领域对象中的国家、型号、错误码、动作和结果使用受控枚举或稳定 ID。用户可见文本由本地化层生成，不作为业务主键。

## 6. 诊断工作流

标准流程必须保持可恢复、可中断和可审计：

```text
接收请求
  -> 语言/意图/实体识别
  -> 身份与设备确认
  -> 授权检查
  -> 安全预分流
  -> 获取最少必要证据
  -> 检索适用知识
  -> 生成/更新候选根因
  -> 选择下一诊断步骤
  -> 执行低风险动作或请求用户操作
  -> 验证结果
  -> 解决 / 继续诊断 / 转人工
  -> 生成报告与工单
  -> 回访和结果回流
```

工作流硬限制：

- 每个诊断回合最多执行一个有副作用的工具。
- 每次工具调用前必须完成权限、参数、风险和幂等校验。
- 每个会话必须配置最大步数、超时和模型预算。
- 工具失败不得被解释为设备故障；必须区分业务失败与基础设施失败。
- 连续两次无新增证据或置信度未提升时，停止循环并转人工。
- 结论必须附依据、适用版本和已执行步骤，不能只输出自然语言判断。

## 7. 知识与检索规则

知识检索必须先做结构化过滤，再做语义召回：

1. 国家或区域；
2. 产品品类；
3. 精确型号及硬件版本；
4. 固件适用范围；
5. 知识状态与生效日期；
6. 语言；
7. 语义相关度与重排。

每条知识必须包含：

- `knowledge_id` 和版本；
- 来源类型与原始出处；
- 适用国家、型号、部件和固件；
- 生效与失效时间；
- 风险级别；
- 是否允许面向消费者展示；
- 审核状态、审核人和审核时间。

禁止：

- 用相似型号的文档代替精确型号而不提示；
- 让 LLM 猜测错误码、保修期或配件兼容性；
- 用网页搜索结果直接驱动高风险售后动作；
- 返回没有可追溯来源的确定性技术结论。

## 8. 工具调用约定

所有外部能力都通过带类型的工具接口暴露，不在提示词或节点中直接调用供应商 SDK。

首批工具接口：

- `resolve_device_identity`
- `get_device_status`
- `get_device_logs`
- `search_product_knowledge`
- `get_order`
- `check_warranty`
- `check_part_compatibility`
- `check_part_inventory`
- `create_or_update_ticket`
- `request_human_review`
- `send_follow_up`

每个工具必须：

- 使用 Pydantic 定义输入与输出；
- 声明只读或有副作用；
- 声明需要的授权范围；
- 配置超时、有限重试和熔断；
- 对有副作用操作接受幂等键；
- 返回稳定错误码，不把异常堆栈暴露给用户；
- 在审计日志中记录脱敏参数、结果和耗时；
- 提供 fake adapter，保证测试不依赖生产系统。

## 9. 安全与人工审核

以下情况立即停止自动诊断并转人工或安全流程：

- 冒烟、烧焦味、漏电、电池膨胀或异常发热；
- 水接近电源、严重漏水或可能造成二次损害；
- 设备已造成人身、宠物或财产损伤；
- 用户要求拆机、短接、绕过安全机构或使用非官方电池；
- 法律投诉、媒体曝光、监管或重大隐私请求；
- 同一问题多次维修仍未解决；
- 疑似批次性或系统性质量事故；
- 设备身份不确定、证据矛盾或诊断置信度不足。

以下动作永远需要人工批准：

- 退款、换新、补偿和拒保；
- 认定人为损坏；
- 固件回滚、远程重置和永久删除用户数据；
- 访问摄像头图像、家庭地图等高敏感数据；
- 超出售后政策的例外处理。

危险场景召回优先于自动解决率。任何优化不得以降低安全召回为代价。

## 10. 多语言与全球化

内部诊断状态统一使用稳定代码和英文技术标识；用户文案再按 locale 本地化。

- 不允许先生成中文结论再机械翻译成其他语言作为唯一方案。
- 政策、质保和服务动作必须根据销售国家与渠道选择。
- 所有日期、货币、单位、电话和地址按 locale 格式化。
- 用户原话与标准症状码同时保存，便于审计和模型改进。
- 翻译失败或语言置信度不足时，保留原文并转人工。
- 采集数据前明确告知用途、范围和保留期限，遵守数据最小化。

## 11. Prompt 与模型规则

- Prompt 存放在版本化文件中，不得散落在业务代码字符串里。
- Prompt 变更必须运行 `tests/evals/`，并记录模型与 Prompt 版本。
- 模型输出必须通过 Pydantic 校验；校验失败应修复或降级，不能直接执行。
- 不要求或保存模型隐藏思维链；只保存简洁的决策依据和引用。
- 面向用户的答复要区分事实、推测和待验证项。
- 模型不得覆盖规则引擎、安全策略或人工决定。
- 模型供应商应通过统一接口接入，业务逻辑不得绑定单一模型。

## 12. API 与错误处理

- API 使用版本前缀，如 `/api/v1/...`。
- 所有响应包含 `request_id`；诊断会话包含稳定 `session_id`。
- 外部可见错误使用稳定错误码和安全描述。
- 日志禁止输出访问令牌、完整序列号、地址、电话、原始家庭图像。
- 可重试错误、用户输入错误、权限错误和系统错误必须分别建模。
- 流式输出只用于展示；最终结构化状态必须落库。

## 13. 测试与评测

任何诊断逻辑变更至少覆盖：

1. 正常路径；
2. 证据缺失；
3. 证据矛盾；
4. 外部工具超时或失败；
5. 型号或固件不匹配；
6. 权限拒绝；
7. 危险场景转人工；
8. 多语言输入；
9. Prompt 注入与恶意工具参数；
10. 最大步数和循环终止。

评测集必须脱敏并分层：

- 高频普通问题；
- 容易混淆的相似症状；
- 罕见但危险的问题；
- 不可回答和知识缺失问题；
- 不同国家、渠道、型号和语言；
- 工具错误及对抗输入。

发布门槛：

- 危险场景不得出现已知漏拦截；
- 工具参数和权限测试 100% 通过；
- 错误配件、错误政策和错误型号引用率接近 0；
- Top-3 根因命中率、知识引用准确率和转人工准确率不得低于当前基线；
- 所有回归测试、静态检查和评测通过。

禁止只用“回答看起来合理”作为验收标准。

## 14. 本地开发与验证闭环

每个实现任务按以下顺序完成：

1. 阅读本文件及任务涉及的 `docs/` 专题文档。
2. 检查现有代码、测试和工作区变更，不覆盖无关修改。
3. 先补充或更新测试，再做最小范围实现。
4. 执行格式化和静态检查。
5. 运行相关单元、集成和安全测试。
6. 启动服务，用独立请求验证真实接口。
7. 对 Agent 行为运行至少一个成功案例和一个升级案例。
8. 检查日志、引用、审计事件和敏感数据脱敏。
9. 汇报变更、验证结果、遗留风险和未执行的检查。

如果由于缺少外部凭据无法完成真实集成验证，使用 fake adapter 完成契约验证，并明确说明未验证的真实系统范围。

## 15. 编码与变更硬规则

- 优先小而可审查的改动，不为未来需求提前建立复杂抽象。
- 业务决策不得隐藏在路由、Prompt 或供应商适配器中。
- 纯领域逻辑优先使用纯函数，并以单元测试覆盖。
- 禁止以自由文本在模块之间传递关键业务状态。
- 禁止静默吞掉异常、自动放宽权限或回退到不匹配知识。
- 禁止在测试中访问真实用户、生产 IoT、CRM 或订单系统。
- 数据库与 API 变更应向后兼容；破坏性变更必须有迁移方案。
- 新增有副作用工具时，必须同时新增权限、幂等、审计和失败测试。
- 修复线上 bad case 时，必须将其转化为回归测试或评测样本。
- 未运行的测试不得描述为已通过。

## 17. 参考资料优先级

发生冲突时按以下顺序处理：

1. 已批准的安全、隐私与法务政策；
2. 结构化产品主数据、固件和错误码数据；
3. 经审核的官方维修 SOP 与服务政策；
4. 当前型号和版本的官方手册；
5. 已闭环且根因明确的历史维修案例；
6. 客服 FAQ 和培训材料；
7. 论坛、评论及其他非官方信息。

非官方信息只能用于提出待验证假设，不能直接支持高风险动作。

## 18. 完成定义

任务只有在以下条件满足时才算完成：

- 实现与需求范围一致；
- 相关测试和评测已通过；
- 诊断过程可审计、可中断、可恢复；
- 安全规则和人工审核未被绕过；
- 新知识、工具或规则具有版本和来源；
- 文档与代码保持一致；
- 没有引入真实秘密或未脱敏用户数据；
- 最终说明包含验证证据与已知限制。
